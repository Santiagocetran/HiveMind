## 0. TL;DR

- The "hive mind" idea — a shared, user-owned memory layer underneath multiple specialized agents — is **real, important, and one of the genuinely unsolved layers** of the agent era.
- The original `hivemind-first-plan.md` (generated by Grok) is **directionally right but uncritical**: its people/projects/repos are all real (verified), but it has a few factual errors and glosses over the part that's actually hard.
- The hard problem is **not** storage or retrieval. It's the **write/curation policy** ("what gets written, by whom, when") and **separation of concerns**.
- The strongest piece of thinking found is the **superada.ai "Files for truth, search for recall"** article, which provides the layered architecture the original doc was missing.
- Best single idea in the whole set: **"Files = truth."** Canonical truth lives in inspectable, versioned markdown files; the graph and vector index are *derived, disposable projections* you can rebuild.

## 1. The Core Idea (the "Hive Mind")

**Origin:** Pejman Pour-Moezzi (@pejmanjohn), X post `2061091767030825003` (May 31, 2026). In Garry Tan's orbit (gstack / office-hours). The post and author are **real** (verified).

**Thesis (stripped of poetry):** AI agents are stateless strangers. Re-establishing context on every handoff is a tax that — unlike with humans — is technically avoidable. The fix is a shared, user-owned memory layer all agents read from and write to, so a learning by one is instantly available to all.

**The illustrative workflow from the post:**
- **OpenClaw** → personal assistant / idea development (richest life context)
- **Codex** → code building (sees repo + plan, misses deep reasoning)
- **Claude Code** → design, writing, landing pages (gets files, not the "why")

**The "repo fallacy":** Markdown/Git capture the *destination* (final decisions), not the *journey* (false starts, abandoned branches, the reasoning that later becomes relevant again).

All the named projects are **real** — this is not a Grok hallucination:

| Pejman Pour-Moezzi / the X post | ✅ Real | author and post ID both exist |

**But two factual errors in the implementation plan (Section 6):**

1. **GBrain does NOT require a Postgres + pgvector server.** Its *default* is **PGLite** (Postgres 17 compiled to WASM, "ready in 2 seconds," no server/Docker, good to ~50K pages). Real Postgres + pgvector is only needed for *shared/distributed* deployments — which is, ironically, exactly the multi-machine hive-mind case.
2. **"Direct integration" is filler.** The real mechanism is **MCP**: GBrain exposes **30+ tools over MCP**, and Hermes **supports MCP servers**. Setup is *agent-directed* — you hand your agent `INSTALL_FOR_AGENTS.md` and it installs, creates the DB, loads ~43 skills, and wires the "dream cycle" background jobs (~30 min).

**Conceptual blind spot:** The doc frames it as "instead of each agent having private memory, build a shared layer." But **Hermes already ships a rich memory system** (Honcho dialectic user modeling, FTS5 session search, a closed learning loop that auto-creates/refines skills). So bolting on GBrain gives Hermes a *second* memory system → risk of two sources of truth. (Mostly resolved by the layered model in §4.)

## 3. Critical Take on the Idea Itself

The vision is right, but four things the original doc treats as settled deserve push-back:

1. **"Journey, not just destination" is the sharpest point — and the recommended stack quietly abandons it.** GBrain (recommended *primary*) is a *destination* system (distills to a knowledge graph). The only tool that preserves the *journey* (raw session logs) is **CASS**, ranked *second*. That ordering is backwards if journey-replay is what you care about.

2. **The hard problem is the write policy, not storage/retrieval.** Storage is solved (Postgres/SQLite/pgvector). Retrieval is mostly solved (hybrid search). What's unsolved: *what deserves to be written, by whom, when?* Dump everything → context pollution → worse retrieval. The "isolated human skull" is also a *feature*: forgetting/filtering is how humans avoid drowning in their own history.

3. **Conflict & staleness have no clean answer.** When facts change, who reconciles the graph? Concurrent writes to one brain = distributed-systems / eventual-consistency headaches. GBrain's "overnight consolidation" + "self-fixing citations" are real attempts, not a solved problem. Good mental model: this is a **memory hierarchy / cache-coherence** problem (working memory → session cache → consolidated long-term store).

4. **Centralization is both the dream and the risk.** "User-owned single source of truth" = great for coherence/ownership, but also a single point of failure, a juicy privacy target, and a lock-in vector.

**Net:** The differentiator between a useful hive mind and an expensive liability is **curation discipline**, not the choice of database or tool. The original doc is ~80% tool selection / ~20% policy; the ratio should be inverted.

## 4. The Best Source: superada.ai — "Files for Truth, Search for Recall"

URL: https://superada.ai/blog/files-for-truth-search-for-recall/

This is the **engineering layer** the Grok doc was missing. It argues sustainable agent crews need **architectural discipline**, not bigger context windows — and imposes **separation of concerns** as the organizing principle.

### The layered memory stack

| Layer | Tool (in their impl) | Job | Principle |
|---|---|---|---|
| 1. Crew Home | shared filesystem | canonical artifacts, plans, outputs | **Files = truth** |
| 2. QMD | search index | fast retrieval over the corpus | **Search = recall** |
| 3. GBrain | graph DB | entities & relationships, *curated not exhaustive* | **Graph = relationships** |
| 4. Honcho | user model | preferences, conversational continuity | **Honcho = continuity** |
| 5. Mission Control | task tracker | turn memory into tracked work | governance |

### Why this matters

- **Resolves the GBrain/Hermes collision:** Honcho (which Hermes already uses) owns *continuity/preferences*; GBrain owns *relationships*. They're complementary **by design**, not redundant. Concern downgrades from "architectural flaw" → "watch the seam" (keep GBrain curated; don't let it hoard preference facts that belong in Honcho).
- **Gives the curation policy a concrete rule:** *"pick one repeated handoff, make the output land in one durable place, index it, and force the next agent to search before acting."* "Search before acting" = the read/write policy in one phrase.
- **Names the failure mode to avoid:** *"an agent that remembers random facts, forgets the important artifact, cannot cite its source."*

### The key idea: "Files = truth"

Canonical truth = **inspectable, versioned markdown files (git)**. The graph and vector index are **derived, disposable projections** of that truth. If the graph drifts or embeddings rot → rebuild from files. It's the **CQRS / "source of truth + derived read models"** pattern applied to agent memory. Benefits: debuggable, diffable, portable, not trapped in one vendor's DB. **Anchor any design on this.**

### Stay critical about superada too

1. **The journey is STILL not captured.** All four layers are artifact-/fact-oriented. "Files = truth" is *destination* truth (final outputs); Honcho is continuity, not replayable reasoning. None preserve the *journey*. **CASS / `cass_memory_system` remains the only thing that does** — treat it as a missing 6th layer (*episodic*).
2. **It's a vendor blog.** Ada is selling the operating-discipline story. **QMD** (their "fast recall" layer) appears to be their own piece and isn't well specified. The stats (55,558 files / 616,383 vectors) are marketing receipts, not a benchmark. The *architecture* is sound and tool-agnostic; any hybrid search index fills the QMD slot.

## 5. Recommended Target Architecture (corrected "Section 6")

A clean layered target, mostly *additive* to Hermes rather than fighting it:

| Layer | Implementation | Notes |
|---|---|---|
| **Truth** | git repo of markdown artifacts | This is "Obsidian vault done right"; also how GBrain stores its brain, so they align |
| **Recall** | hybrid search index over that repo | GBrain ships one; or CASS |
| **Relationships** | GBrain graph (kept *curated*) | PGLite by default; real Postgres+pgvector only if going multi-machine |
| **Continuity** | Honcho | **Hermes already runs this — free** |
| **Episodic / journey** | CASS / `cass_memory_system` | The layer superada omits; only if journey-replay matters |
| **Governance** | task tracker (optional) | Only if coordinating multiple agents on real workstreams |

### How the Hermes setup will actually play out (prediction)

- **Setup:** smooth. PGLite default + agent-run installer + MCP registration. ~1–2 hrs (maybe less).
- **First impression:** feels great — cross-agent recall is a genuine "wow" moment.
- **Week 2–4 reality:** curation problem + Hermes/GBrain seam surface — noise, occasional contradictory recall, uncertainty over which system "owns" a fact. This is where people either define a write-policy and recover, or quietly stop trusting it.
- **The fix:** decide the layer separation up front (the table above). "Install all three and point them at each other" is not an architecture; the layered hierarchy is.

## 7. OPEN QUESTIONS (for you to answer / investigate)

These change the recommendation a lot:

1. **What's your real setup today?** Are you actually running Hermes (or OpenClaw)? On how many machines, alongside which other agents (Claude Code, Codex, Cursor)? → The cross-machine angle is what tips you from PGLite to real Postgres.

2. **What's the goal — personal leverage, or building a product?** "Make my own agents share context" vs. "build the hive-mind layer as a thing" → very different work.

3. **Journey or destination?** Structured recall of *facts/people/projects* (→ GBrain leads) vs. faithful replay of *how you got somewhere* across past sessions (→ CASS / cass-memory leads)? Be honest about which actually hurts more right now. **This decides whether you need the CASS/episodic layer at all.**

4. **Privacy / self-hosting constraints?** Decides whether Supermemory (cloud) is even on the table, and how paranoid the central-brain design needs to be.
